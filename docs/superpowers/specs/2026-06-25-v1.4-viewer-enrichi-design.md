# Spec v1.4 « Viewer enrichi »

> Établie le 2026-06-25. Sous-projet de la feuille de route
> (`docs/superpowers/specs/2026-06-21-roadmap.md`). Cycle : cette spec →
> plan → implémentation (subagent-driven-development).

## Objectif

Enrichir le rendu du viewer local sans rompre l'ethos du projet (bibliothèque
standard uniquement, hors-ligne, zéro dépendance externe côté viewer) :

- **V2** — rendu Markdown des fichiers `.md`/`.markdown` (aujourd'hui servis en
  texte brut).
- **V7** — coloration syntaxique multi-langages (aujourd'hui : Python seul).

**Hors périmètre v1.4** (décidé) : V5 favoris/annotations (reporté), rendu
LaTeX/math (écarté, cf. V3), notebooks `.ipynb` (écarté, cf. V4).

## Contraintes & principes

- **Stdlib uniquement, hors-ligne.** Aucun ajout à `requirements.txt`. Pas de
  blob JS vendorisé (marked.js / highlight.js exclus). Tout le rendu se fait
  **côté serveur en Python pur**, sur le modèle du coloriseur Python existant
  (`colorier_python`, basé sur `tokenize`, dans `cdp_viewer.py`).
- **Non-régression.** Le comportement actuel reste un repli valide : `.py` →
  page `/code/` colorisée ; types texte → `text/plain` ; le 500 d'API reste
  JSON. Aucune page ne doit jamais planter (toujours un repli texte brut).
- **Sécurité.** Le contenu provient de cahier-de-prepa : il est **non fiable**.
  Tout texte est échappé avant insertion de balises ; aucune balise HTML de la
  source n'est propagée ; les URL sont assainies ; l'accès reste confiné au
  dossier des cours autorisé.
- **Isolation / testabilité.** Nouvelles fonctionnalités dans des modules Python
  purs testables sans serveur ni réseau, sur le modèle de `cdp_manifeste.py` et
  `cdp_config.py`.

## Architecture

Deux nouveaux modules Python purs ; `cdp_viewer.py` orchestre.

| Module | Rôle | Signature principale |
|---|---|---|
| `cdp_markdown.py` | Convertisseur Markdown → HTML (V2) | `convertir(source: str, prefixe_url: str) -> str` |
| `cdp_coloration.py` | Coloriseur générique multi-langages (V7) | `colorier(source: str, langage: str) -> str | None` |

- Le coloriseur Python existant (`colorier_python` via `tokenize`) **reste dans
  `cdp_viewer.py`** et garde la priorité pour `.py` (plus précis que le
  générique). `cdp_coloration.py` ne gère **pas** Python.
- Chaque module porte un `VERSION` de schéma (comme `cdp_manifeste`/`cdp_config`),
  pas de SemVer (seuls `cdp_scraper`/`cdp_viewer` ont un `__version__`).

## V2 — Convertisseur Markdown (`cdp_markdown.py`)

### Couverture (« essentiel + tables »)

- **Blocs :** titres `#`…`######` ; paragraphes ; listes à puces (`-`/`*`/`+`) et
  numérotées, **imbriquées** par indentation ; blocs de code clôturés ` ``` `
  avec langage optionnel ; citations `>` ; règles horizontales `---`/`***` ;
  **tables GFM** (`| a | b |` + ligne de séparation `|---|---|`).
- **Inline :** gras `**`/`__` ; italique `*`/`_` ; code `` `code` `` ; liens
  `[texte](url)` ; images `![alt](url)`.

### Sécurité

- Tout le texte est échappé (`html.escape`) avant insertion des balises. Le
  convertisseur n'émet qu'une **liste blanche** de balises (`h1`–`h6`, `p`,
  `ul`/`ol`/`li`, `pre`/`code`, `blockquote`, `hr`, `table`/`thead`/`tbody`/
  `tr`/`th`/`td`, `a`, `img`, `strong`, `em`). Aucun HTML inline présent dans la
  source n'est propagé (il est échappé comme du texte).
- **URL assainies :** liens et images n'autorisent que les schémas `http:` /
  `https:` et les chemins relatifs/locaux. Tout `javascript:`, `data:`, `vbscript:`
  ou schéma inconnu rend le lien **inerte** (texte conservé, pas de `href`/`src`
  actif).
- Liens externes : `rel="noopener noreferrer"`.

### Images locales

`convertir` reçoit `prefixe_url` = URL du dossier du `.md` rendu. Les `src`
relatifs sont résolus vers la route `/file/...` existante. Les chemins qui
sortiraient du dossier autorisé (`../`) sont **rejetés** (cohérent avec l'erreur
« Accès refusé » existante) : l'image est alors rendue inerte.

### Formules mathématiques

Aucun traitement spécial — texte brut (choix assumé, cohérent avec V3 écarté).
*Caveat connu :* un `$a_b$` peut voir son `_` interprété comme italique. C'est
le compromis accepté du choix « rien de spécial ».

### Synergie avec V7

Un bloc ` ```<langage> ` dont le langage est reconnu est passé au coloriseur
adéquat (Python → `colorier_python` ; autres → `cdp_coloration.colorier`) →
code coloré dans le rendu Markdown. Langage absent/inconnu, ou coloriseur
renvoyant `None` : bloc `<pre><code>` simple, échappé.

## V7 — Coloriseur générique (`cdp_coloration.py`)

### Approche

Un **seul moteur regex paramétré par langage**, pas un coloriseur par langage.
Table de specs : chaque langage est décrit par une petite structure (mots-clés,
style de commentaire ligne, commentaire bloc éventuel, délimiteurs de chaîne,
sensibilité à la casse des mots-clés).

Le moteur balaie la source avec **une regex alternée** (module `re`) à groupes
nommés, dans un ordre de priorité évitant les faux positifs : commentaires →
chaînes → nombres → mots-clés → reste. Chaque correspondance devient un
`<span class="…">` réutilisant **les classes CSS déjà présentes** dans
`PAGE_CODE` (`.kw`, `.str`, `.com`, `.num`) — thème clair/sombre gratuit, aucun
CSS nouveau.

### Langages couverts

C, C++, Java, SQL (mots-clés insensibles à la casse), R, OCaml (`.ml`), JSON.
**Python n'est pas géré ici** (reste sur `tokenize`).

### Garanties

- **Préservation exacte** du texte (indentation, espaces) : la source n'est
  jamais réécrite, seuls des segments sont enrobés.
- **Échappement** systématique (`html.escape`) du texte avant insertion des
  `<span>`.
- **Repli sûr :** langage inconnu ou source problématique → `None` ; l'appelant
  affiche le texte brut échappé. Jamais d'erreur 500, jamais de page cassée.

### Limite assumée

La coloration regex est approximative (pas de parsing complet : apostrophe dans
un commentaire, here-docs SQL exotiques, etc.). Compromis stdlib/sans-dépendance ;
le rendu reste lisible et **n'altère jamais le code affiché**.

## Intégration dans `cdp_viewer.py`

### Routes

- `/rendu/<chemin.md>` (nouvelle) → page HTML du Markdown rendu. Nouvelle
  constante `PAGE_RENDU` : en-tête thémé réutilisant le CSS du viewer + bouton
  « Voir la source ».
- `/code/<chemin>` (étendue) → ne sert plus seulement `.py`. Selon l'extension :
  `colorier_python` (py) ou `cdp_coloration.colorier(source, langage)` (c, cpp,
  java, sql, r, ml, json). Repli texte brut si `None`. La page `PAGE_CODE`
  existante est réutilisée ; le bouton « Lancer sur la machine » reste réservé
  à `.py`.

### Liste (JS dans `PAGE_HTML`)

- Ajout de `urlRendu(c)` pour `.md`/`.markdown` (à côté de `urlCode` existant).
- `ligne(noeud)` : un `.md` ouvre `/rendu/` ; un fichier de code reconnu ouvre
  `/code/`. `VISIONNABLES`/`EXT_TEXTE` restent le repli pour le reste.
- Navigation clavier existante (V6) inchangée — les nouvelles vues sont de
  simples liens.

### Bascule source / rendu

Sur `/rendu/`, bouton « Voir la source » → affiche le `.md` brut via la route
`text/plain` actuelle (conservée). Réversible.

- `cdp_scraper.py` et `cdp_viewer.py` → `__version__ = "1.4.0"`.
- Entrée `CHANGELOG.md` (section v1.4).
- Mentions dans `README.md` (rendu Markdown, coloration multi-langages).

## Tests (`unittest`, hors-ligne)

`pytest` n'est pas installé : exécution via
`python -m unittest discover -s tests`.

- `tests/test_markdown.py` : chaque construct (titres, listes imbriquées, tables
  GFM, blocs de code, liens, images) ; **sécurité** (texte échappé, `javascript:`
  neutralisé, HTML inline non propagé, chemin `../` rejeté) ; synergie code+V7.
- `tests/test_coloration.py` : par langage, un échantillon → présence des bons
  `<span>` ; **préservation exacte** (texte dé-balisé == source d'origine) ;
  repli `None` sur langage inconnu ; mots-clés SQL insensibles à la casse.
- Non-régression : `colorier_python` et le rendu actuel intacts (tests
  existants conservés).

## Critères de succès

1. Un `.md` de cours s'affiche formaté (titres, listes, tables, code coloré),
   en respectant le thème clair/sombre.
2. Les fichiers `.c/.cpp/.java/.sql/.r/.ml/.json` s'affichent colorés via
   `/code/` ; `.py` inchangé.
3. Aucune dépendance ajoutée ; tout fonctionne hors-ligne.
4. Aucune injection possible depuis un `.md` (échappement + URL assainies +
   confinement des chemins) — couvert par tests.
5. Toute la suite `unittest` passe ; pas de régression sur les tests existants.

## Périmètre

Le scraper redemande aujourd'hui le mot de passe cahier-de-prepa à **chaque
run et pour chaque classe**, même quand la classe est déjà mémorisée dans
`cdp_config.py` (qui ne stocke jamais le mot de passe, par choix — cf. v1.3).
Pour un usage multi-classes régulier, retaper les mots de passe à chaque fois
est la friction principale.

Objectif : un **coffre chiffré local optionnel** qui permet, après un seul
mot de passe maître saisi en début de run, de retélécharger n'importe quelle
classe déjà mémorisée sans retaper son mot de passe. Fonctionnalité **opt-in**
par classe : rien ne change pour qui ne l'active jamais.

Hors-scope : synchronisation du coffre entre machines, récupération d'un mot
de passe maître oublié (seule option : supprimer le coffre et tout
ré-enregistrer), interface graphique.

## Principes directeurs

- **Opt-in strict, par classe.** Aucun mot de passe n'est chiffré et stocké
  sans une confirmation explicite de l'utilisateur pour *cette* classe.
- **Zéro dépendance par défaut.** La bibliothèque `cryptography` n'est
  installée/importée que si une fonctionnalité du coffre est réellement
  utilisée (une classe sans mot de passe enregistré ne dépend de rien de
  plus qu'aujourd'hui).
- **Confidentialité honnête.** Le texte des conditions d'usage est mis à jour
  pour refléter le nouveau comportement (au lieu d'affirmer à tort que rien
  n'est jamais stocké). Le mot de passe maître n'est lui-même jamais écrit
  sur disque.
- **Cohérence d'architecture.** Nouveau module `cdp_coffre.py`, calqué sur
  `cdp_config.py`/`cdp_manifeste.py` (fonctions pures + I/O atomique
  testables hors-ligne, `VERSION` de schéma interne).
- **Tests 100 % hors-ligne**, dans la lignée des suites existantes.

## 1. Module `cdp_coffre.py`

### Fichier et résolution de chemin

`.cdp-scraper/coffre.json`, même cascade que `cdp_config.chemin_config`
(override `--coffre CHEMIN` → `./.cdp-scraper/coffre.json` si présent →
`~/.cdp-scraper/coffre.json`). Fonction `chemin_coffre(override=None) -> Path`
sur le même modèle.

### Cryptographie

- **Dérivation de clé** : Scrypt (`cryptography.hazmat.primitives.kdf.scrypt.Scrypt`,
  n=16384, r=8, p=1) à partir du mot de passe maître + un sel aléatoire de 16
  octets stocké en clair dans le fichier (le sel n'est pas un secret).
  Produit une clé de 32 octets (AES-256).
- **Chiffrement** : AES-256-GCM (`AESGCM`), un nonce aléatoire de 12 octets
  par entrée, le **nom de la classe en associated data** (empêche de
  substituer le blob chiffré d'une classe à celui d'une autre).
- **Témoin** (`temoin`) : une constante fixe (`b"cdp-coffre-ok"`) chiffrée
  avec la clé dérivée au moment de la création du coffre. Sert à détecter un
  mauvais mot de passe maître (échec de déchiffrement / tag GCM invalide)
  sans avoir besoin de posséder déjà une vraie entrée.
- Le mot de passe maître ne transite qu'en mémoire process, jamais sur
  disque.

### Schéma du fichier

```json
{
  "version": 1,
  "kdf": {"algorithme": "scrypt", "sel": "<base64 16 octets>", "n": 16384, "r": 8, "p": 1},
  "temoin": {"nonce": "<base64>", "chiffre": "<base64>"},
  "entrees": {
    "mpsi": {"nonce": "<base64>", "chiffre": "<base64>"}
  }
}
```

### API

- `charger(chemin: Path) -> dict` — absent/illisible → coffre vide
  `{"version": 1, "entrees": {}}` (pas de `kdf`/`temoin` tant qu'aucun mot de
  passe n'a jamais été enregistré). Version de schéma supérieure → lève
  `CoffreVersionFuture`.
- `enregistrer(chemin: Path, coffre: dict) -> None` — écriture atomique
  (`.part` → renommage), comme `cdp_config.enregistrer`.
- `est_initialise(coffre: dict) -> bool` — présence de `kdf`/`temoin`.
- `creer(mdp_maitre: str) -> dict` — nouveau coffre (sel + témoin générés),
  utilisé au tout premier `ajouter`.
- `deverrouiller(coffre: dict, mdp_maitre: str) -> bytes` — dérive la clé,
  vérifie le témoin, lève `MotDePasseMaitreIncorrect` si le déchiffrement du
  témoin échoue.
- `ajouter(coffre: dict, mdp_maitre: str, nom: str, mdp_classe: str) -> dict`
  — initialise le coffre si besoin (premier usage), sinon `deverrouiller`,
  puis chiffre `mdp_classe` sous la clé et l'enregistre dans
  `entrees[nom]`.
- `recuperer(coffre: dict, mdp_maitre: str, nom: str) -> str` —
  `deverrouiller` puis déchiffre `entrees[nom]`. Lève
  `MotDePasseMaitreIncorrect` ou `ClasseAbsenteDuCoffre`.
- `retirer(coffre: dict, nom: str) -> dict` — supprime l'entrée si présente
  (aucun mot de passe maître requis pour une suppression).
- `contient(coffre: dict, nom: str) -> bool`
- `lister(coffre: dict) -> list[str]` — noms des classes ayant un mot de
  passe enregistré. **Jamais** les mots de passe.
- `changer_mdp_maitre(coffre: dict, ancien: str, nouveau: str) -> dict` —
  `deverrouiller` avec `ancien`, déchiffre toutes les entrées, régénère
  sel + témoin, rechiffre tout sous la clé dérivée de `nouveau`.

### Dépendance

`cryptography` ajoutée à `_assurer_dependances` (même mécanisme que
`requests` : détection + proposition d'installation pip), mais appelée
**seulement** depuis les chemins de code qui utilisent effectivement le
coffre (les nouveaux flags `--coffre-*`, et la question d'activation décrite
en §3). Un usage du scraper qui n'active jamais le coffre n'installe rien de
plus qu'aujourd'hui.

## 2. Intégration CLI (`cdp_scraper.py`)

### Nouveaux arguments

| Argument | Rôle |
|---|---|
| `--coffre CHEMIN` | Force le chemin du fichier coffre (défaut : cascade, cf. §1) |
| `--coffre-ajouter NOM` | Enregistre/remplace le mot de passe d'une classe déjà mémorisée dans la config (demande le mot de passe maître — création si premier usage — puis le mot de passe de la classe, masqué) puis quitte |
| `--coffre-supprimer NOM` | Retire le mot de passe d'une classe du coffre puis quitte |
| `--coffre-lister` | Affiche les noms de classes ayant un mot de passe enregistré (jamais les mots de passe) puis quitte |
| `--coffre-changer-mdp` | Redéchiffre tout le coffre sous un nouveau mot de passe maître (demande l'ancien puis le nouveau) puis quitte |

Ces commandes de gestion suivent le même patron que `--config-lister` /
`--config-supprimer` (exécutées puis `return` immédiat dans `main`).

`--config-supprimer NOM` retire **aussi** l'entrée coffre correspondante si
elle existe (`cdp_coffre.retirer`), pour ne jamais laisser un secret chiffré
orphelin d'une classe qui n'existe plus dans la config.

### Champ de config `coffre_propose`

Nouveau champ non sensible dans chaque entrée de `cdp_config.json` :
`"coffre_propose": true`. Signifie « la question d'activation du coffre a
déjà été tranchée pour cette classe (par oui ou par "ne plus jamais
demander") » — voir §3 pour la sémantique exacte des trois réponses
possibles. Absence du champ = jamais tranchée (y compris pour une classe
mémorisée par une version antérieure du script, avant l'existence de ce
champ).

### Flux d'activation, une fois par classe (§3)

Décrit en détail ci-dessous — s'applique aussi bien au mode mono-classe
(`run_classe_unique`) qu'au mode multi-classes (`main`), immédiatement après
le traitement de **cette classe précise** (même emplacement que la question
existante « Mémoriser la classe dans la config ? »). Dans une boucle
multi-classes, la question est donc posée à la suite de chaque classe
concernée, avant de passer à la suivante — pas une seule fois à la toute fin
du run global.

### Flux d'utilisation du coffre au lancement (boucle multi-classes de `main`)

Concerne la boucle `for cfg in choisies:` (ligne actuelle ~935) :

1. Si `--mdp` est fourni en ligne de commande → comportement inchangé
   (aucune question sur le coffre, ce flag reste une valeur imposée pour
   toutes les classes du run).
2. Sinon, si **au moins une** classe de `choisies` a une entrée dans le
   coffre (`cdp_coffre.contient`) :
   - une question unique pour le run : « Utiliser le coffre chiffré pour
     déverrouiller les mots de passe enregistrés ? [O/n] ».
   - **Oui** → demande le mot de passe maître, **jusqu'à 3 essais** contre le
     témoin (`MotDePasseMaitreIncorrect`). Dès validation, chaque classe
     présente dans le coffre est déverrouillée automatiquement pour ce run
     (`cdp_coffre.recuperer`) — plus aucune saisie pour elles.
   - **3 échecs** → repli en saisie manuelle pour les classes concernées,
     avec un message explicite (« mot de passe maître incorrect à 3
     reprises, saisie manuelle pour la suite »).
   - **Non** → saisie manuelle comme aujourd'hui, pour toutes les classes.
3. Les classes **absentes** du coffre demandent toujours leur mot de passe
   manuellement, indépendamment du choix ci-dessus.

Le mode mono-classe (`run_classe_unique`, atteint via `--url` ou config
vide) ne bénéficie pas de ce flux multi-classes par construction (une seule
classe traitée) : le mot de passe est toujours demandé une fois normalement
avant traitement, et l'activation du coffre est seulement **proposée après**
(§3), pour un usage futur.

## 3. Proposer le coffre — trois réponses, une seule fois par classe

À la suite du traitement de chaque classe (mono ou multi), si
`coffre_propose` est absent ou faux pour cette classe **et** que l'entrée
standard est un terminal interactif (`sys.stdin.isatty()` — pas de question
bloquante dans un contexte scripté/non interactif) :

```
Enregistrer le mot de passe de « <nom> » dans le coffre chiffré ?
  [o] Oui, l'enregistrer maintenant
  [n] Non, redemander la prochaine fois   (défaut)
  [j] Non, ne plus jamais demander pour cette classe
Choix [o/n/j] :
```

- **o** — Enregistrement immédiat : mot de passe maître demandé (création du
  coffre si c'est le tout premier usage) ; le mot de passe de la classe est
  déjà en mémoire pour ce run (pas besoin de le ressaisir) ; `cdp_coffre.ajouter`
  puis `coffre_propose: true` écrit dans la config.
- **n** ou Entrée — Rien n'est stocké, **`coffre_propose` reste absent** :
  la question sera reposée au prochain traitement de cette classe.
- **j** — Rien n'est stocké, mais `coffre_propose: true` est écrit
  immédiatement, avec un rappel affiché : « Vous pourrez l'activer plus tard
  avec `--coffre-ajouter <nom>`. » La question ne sera plus jamais posée
  automatiquement pour cette classe (le choix reste réversible via la
  commande dédiée).

Si `--mdp` a été fourni en ligne de commande pour ce run (mot de passe
imposé, pas nécessairement le vrai mot de passe habituel de l'utilisateur
selon le contexte), la question n'est **pas** posée : on ne propose
d'enregistrer que le mot de passe effectivement saisi/validé au clavier pour
cette classe.

**Un seul mot de passe maître par run.** Que le déverrouillage ait eu lieu
en amont (§2, pour retélécharger des classes déjà dans le coffre) ou soit
déclenché ici pour la première fois (« o », création ou ajout), le mot de
passe maître une fois validé reste en mémoire pour le reste du run : il
n'est jamais redemandé deux fois dans le même run, y compris si plusieurs
classes différentes déclenchent chacune une opération sur le coffre.

## 5. Tests

### `tests/test_cdp_coffre.py` (hors-ligne, sans dépendance réseau)

- Coffre absent/vide → `charger` renvoie une structure vide, pas d'erreur.
- `creer` + `ajouter` + `recuperer` avec le bon mot de passe maître → round-trip
  correct.
- Mauvais mot de passe maître → `deverrouiller`/`recuperer` lèvent
  `MotDePasseMaitreIncorrect` (témoin invalide).
- `ClasseAbsenteDuCoffre` si `recuperer` sur un nom absent.
- `retirer` puis `contient`/`lister` reflètent la suppression.
- `changer_mdp_maitre` : l'ancien mot de passe maître échoue après coup, le
  nouveau fonctionne, les entrées existantes restent lisibles avec le
  nouveau mot de passe.
- Écriture atomique (`enregistrer` ne laisse pas de `.part` résiduel).
- Résolution cascade de `chemin_coffre` (identique au test existant pour
  `chemin_config`).
- Version de schéma future → `CoffreVersionFuture`.

### `tests/test_cdp_scraper.py` (ajouts)

- Logique des trois réponses o/n/j isolée (fonction pure testable sans
  input() réel ni réseau) : `o` enregistre + marque `coffre_propose`, `n` ne
  marque rien, `j` marque sans enregistrer.
- `coffre_propose` absent (classe mémorisée par une version antérieure) →
  traité comme jamais tranché.
- Non-interactif (`sys.stdin.isatty()` faux) → aucune question posée, aucun
  champ modifié.
- Boucle multi-classes : au moins une classe dans le coffre → question
  unique posée puis déverrouillage réutilisé pour toutes les classes
  concernées ; classes absentes du coffre toujours en saisie manuelle ;
  3 échecs de mot de passe maître → repli manuel avec message explicite.
- `--config-supprimer NOM` retire aussi l'entrée coffre correspondante.
- `--coffre-lister`/`--coffre-ajouter`/`--coffre-supprimer`/`--coffre-changer-mdp`
  exécutés puis sortie immédiate (comme les tests existants pour
  `--config-lister`/`--config-supprimer`).

## Compatibilité

- Sans jamais répondre « o » à la question d'activation (ou sans jamais
  utiliser `--coffre-ajouter`), le comportement est **strictement
  identique** à aujourd'hui : mot de passe toujours redemandé, aucune
  dépendance supplémentaire installée.
- `.gitignore` couvre déjà `.cdp-scraper/` : `coffre.json` ne sera jamais
  suivi par git, comme `config.json` aujourd'hui.
- `cdp_config.py` et `cdp_manifeste.py` restent inchangés à l'exception du
  nouveau champ optionnel `coffre_propose` (rétrocompatible : absent chez
  les classes existantes, traité comme « jamais tranché »).

## Critères de réussite

- Une classe déjà mémorisée avant cette version se voit proposer
  l'activation du coffre au prochain traitement (mono ou multi-classes).
- Répondre « o » permet, lors d'un run ultérieur, de retélécharger cette
  classe après une seule saisie du mot de passe maître, sans retaper son
  mot de passe cahier-de-prepa.
- Répondre « n » repose la question au prochain run ; répondre « j » ne la
  repose plus jamais, mais `--coffre-ajouter <nom>` reste disponible pour
  changer d'avis.
- Un mot de passe maître incorrect ne fait jamais planter le run : après 3
  essais, repli sur la saisie manuelle.
- Sans usage du coffre, aucune dépendance supplémentaire n'est installée et
  le comportement est identique à la v1.4.
- Suite de tests hors-ligne verte sur la CI existante.

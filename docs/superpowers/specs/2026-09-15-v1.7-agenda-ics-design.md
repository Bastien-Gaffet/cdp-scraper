# Spec — v1.7 « Agenda → export .ics »

> Établie le 2026-09-15. Sous-projet de la feuille de route
> (`docs/superpowers/specs/2026-06-21-roadmap.md`, pas encore listé — à
> ajouter au merge). Cycle *spec → plan → implémentation → revue*. Cible de
> version : **1.7.0**.

## Périmètre

Le site *Cahier de prépa* propose un agenda de classe (`agenda.php`), où les
professeurs programment les devoirs surveillés (DS), devoirs maison, cours
particuliers, vacances, etc. Aujourd'hui `cdp-scraper` ne récupère que les
documents (`docs`) et les programmes de colles : l'agenda n'est pas exploré.

Objectif : pouvoir importer dans un calendrier externe (Google Calendar en
premier lieu) les dates de DS programmées sur toute l'année scolaire, sans
ressaisie manuelle.

En deux parties :

1. **Scraper** : un nouveau module `cdp_agenda.py` récupère l'agenda de la
   classe (authentification réutilisée, comme pour `docs`/programmes de
   colles), filtre les devoirs surveillés et écrit un fichier `.ics`
   (RFC 5545) à côté des documents de la classe.
2. **Viewer** : une page « Calendrier » affiche les événements retenus et
   permet de télécharger le `.ics` généré, prêt à importer dans Google
   Calendar (*Paramètres → Importer et exporter → Importer*).

Hors-scope : édition de l'agenda (lecture seule, jamais d'écriture vers
cahier-de-prepa.fr) ; abonnement « live » par URL (`webcal://`) — le viewer
tourne en local (`127.0.0.1`), non joignable depuis Google ; export d'autres
types d'événements que les DS dans l'interface (voir note de conception
ci-dessous sur le filtre) ; toute notion de couleur/rappel personnalisés dans
l'`.ics`.

## Principes directeurs

- **Zéro dépendance ajoutée.** Parsing HTML par expressions régulières,
  comme le fait déjà `cdp_scraper.analyser_page` pour les documents — pas de
  BeautifulSoup. Génération de l'`.ics` à la main (format texte simple), pas
  de librairie `icalendar`.
- **Réutilise la session déjà authentifiée.** `cdp_agenda.recuperer_agenda`
  reçoit la `requests.Session` déjà connectée par `cdp_scraper.connexion` —
  aucune nouvelle authentification, aucun nouveau champ de config.
- **Filtre DS non figé dans une liste blanche exacte.** Le nom du type
  d'événement est configurable par chaque classe/prof (`agenda-types.php`
  côté cahier-de-prepa) ; la valeur par défaut du logiciel est *« Devoir
  surveillé »*. Le filtre retient tout type dont le nom normalisé (minuscules,
  sans accents) contient `surveille` — couvre le défaut sans être une
  correspondance exacte trop fragile si le nom est légèrement modifié.
- **Résistant aux deux modes d'affichage de la page agenda.** Un compte élève
  standard (lecture seule) et un compte avec droits d'édition sur l'agenda
  n'ont pas exactement le même HTML pour le bloc détaillé d'un événement (cf.
  §1). Le parseur doit gérer les deux sans planter, en préférant la source la
  plus fiable quand elle est disponible.
- **Idempotent par identifiant d'événement.** Chaque événement porte un
  `data-id` stable côté cahier-de-prepa ; le même événement vu sur plusieurs
  mois (semaines à cheval sur deux mois) ne doit apparaître qu'une fois dans
  l'`.ics` généré.
- **Jamais dans l'arborescence de documents du viewer.** Le fichier généré
  est préfixé d'un point (`.agenda.ics`) pour rester invisible dans
  `/api/tree` et `/api/classes` (déjà filtrés sur `startswith(".")`, comme le
  manifeste), et n'est exposé qu'via la nouvelle route dédiée du viewer.
- **Tests 100 % hors-ligne** : pages HTML synthétiques en fixtures, aucun
  appel réseau réel vers cahier-de-prepa.fr dans les tests.

## 1. Récupération et analyse : `cdp_agenda.py`

### Ce que renvoie la page `agenda.php`

Chaque mois est demandé via `GET {base}/agenda?mois=YYMM` (`YY` = année sur 2
chiffres, `MM` = mois sur 2 chiffres, ex. `2609` pour septembre 2026 — format
confirmé en lisant `agenda.php` sur le dépôt source du logiciel,
`https://forge.apps.education.fr/cyrilravat/cahier-de-prepa`). La page
contient, pour chaque événement visible, un bloc détaillé sous le tableau du
calendrier :

```html
<article data-id="123">
  <h3 class="titreagenda">Le vendredi 12 septembre 2026 à 8h</h3>
  <h4>Devoir surveillé en Mathématiques</h4>
  <p>Texte libre, éventuellement avec des balises HTML…</p>
</article>
```

(compte en lecture seule, cas normal pour un élève) — ou, pour un compte
disposant de droits d'édition sur l'agenda :

```html
<article data-id="123" data-protection="0" data-edition="0">
  <p class="titreagenda edition" data-donnees='{"tid":4,"mid":2,
     "debut":"12/09/2026 8h00","fin":"12/09/2026 8h00","jours":false}'>
    Le vendredi 12 septembre 2026 à 8h<br>Devoir surveillé en Mathématiques
  </p>
  …
</article>
```

Le second cas fournit une date **structurée** (`data-donnees`) — bien plus
fiable qu'un texte en français à parser. Le parseur essaie donc d'abord
d'extraire `data-donnees` ; à défaut, il retombe sur le texte de
`<h3 class="titreagenda">` (ou `<p class="titreagenda">` en mode édition).

Chaque événement apparaît aussi dans la grille du calendrier, avec un titre
au format `"{matière} - {type}"` (séparateur ` - `, différent du ` en ` du
bloc détaillé) :

```html
<td data-id="123"><p class="evnmt4">Mathématiques - Devoir surveillé</p></td>
```

Ce second format sert à séparer matière et type de façon fiable (le
séparateur ` en ` du bloc détaillé serait ambigu si un nom de matière
contenait lui-même ce mot).

### API du module

```python
def mois_annee_scolaire(aujourdhui: date) -> list[tuple[int, int]]:
    """10 couples (année, mois) de septembre à juin, sur l'année scolaire
    contenant `aujourdhui` (bascule au 1er juillet)."""

def recuperer_agenda(session: requests.Session, base: str,
                      aujourdhui: date | None = None, delai: float = 0.0) -> list[dict]:
    """Parcourt agenda?mois=YYMM pour chaque mois de l'année scolaire,
    fusionne les événements par data-id (un même DS à cheval sur deux
    semaines de mois différents n'apparaît qu'une fois). Renvoie une liste de
    dicts : {id, type, matiere, debut: datetime, fin: datetime|None,
    journee_entiere: bool, texte: str}."""

def analyser_page_agenda(html_page: str) -> list[dict]:
    """Analyse une seule page mensuelle (regex, pas de dépendance). Combine
    bloc grille (type/matière) et bloc détaillé (date/texte), avec repli sur
    data-donnees si présent."""

def filtrer_ds(evenements: list[dict]) -> list[dict]:
    """Garde les événements dont le type normalisé contient 'surveille'."""
```

`analyser_page_agenda` doit rester silencieuse (liste vide) sur une page où
l'agenda est désactivé pour ce compte (`agenda_protection` empêche l'accès :
absence de blocs `<article data-id=...>`) — pas d'erreur, comme
`crawler_progcolles` qui tolère déjà une classe sans colles.

## 2. Génération du fichier : format `.ics`

```python
def generer_ics(evenements: list[dict], nom_classe: str) -> str:
    """RFC 5545 minimal : VCALENDAR/VEVENT, pliage de ligne à 75 octets,
    échappement des caractères spéciaux (, ; \\ et retours à la ligne)."""
```

- `UID` stable : `f"cdp-agenda-{slug(nom_classe)}-{id}@cdp-scraper.local"` —
  permet de reconnaître le même événement d'un export à l'autre (utile si on
  réimporte, voir limite connue ci-dessous).
- `DTSTAMP` : horodatage de génération (UTC).
- `SUMMARY` : `"{type} en {matière}"` ou juste `{type}` sans matière.
- `DESCRIPTION` : texte libre de l'événement, balises HTML retirées
  (réutilise le même principe que `cdp_scraper._texte`), échappé pour l'ICS.
- Dates :
  - Journée entière (`jours: true` ou pas d'heure détectée) :
    `DTSTART;VALUE=DATE` / `DTEND;VALUE=DATE` (borne exclue, donc `fin + 1
    jour` pour un événement d'un seul jour).
  - Horodaté : `DTSTART;TZID=Europe/Paris` / `DTEND;TZID=Europe/Paris`. Si une
    seule heure est visible (heure de début = heure de fin affichée), on ne
    connaît pas la vraie durée : **hypothèse par défaut d'une durée de 4
    heures** (durée typique d'un DS de prépa), à ajuster si besoin une fois
    testé sur un vrai agenda.

## 3. Intégration `cdp_scraper.py`

- Import `cdp_agenda` en tête de fichier.
- Nouveau flag `--sans-agenda` (`action="store_true"`), même logique que
  `--sans-colles` : **activé par défaut**, désactivable explicitement.
- Dans `traiter_classe`, après la récupération des documents (ou en
  parallèle logique, mais après une connexion réussie) :

```python
if not args.sans_agenda:
    evenements = cdp_agenda.filtrer_ds(cdp_agenda.recuperer_agenda(session, url))
    if evenements:
        contenu = cdp_agenda.generer_ics(evenements, nom_classe)
        if not simulation:
            dossier.mkdir(parents=True, exist_ok=True)
            _ecrire_atomique(dossier / ".agenda.ics", contenu)
        print(f"  {len(evenements)} devoir(s) surveillé(s) → .agenda.ics")
```

(écriture atomique `.part` → renommage, même pattern que
`cdp_manifeste`/`cdp_config`.) Une erreur réseau pendant la récupération de
l'agenda ne doit jamais faire échouer le run global (récupération des
documents indépendante) — comportement toléré comme pour les colles,
message d'avertissement affiché puis on continue.

## 4. Intégration `cdp_viewer.py`

Nouvelle route `GET /calendrier/<classe>` : lit `.agenda.ics` dans le
dossier de la classe (résolu avec `resoudre_dans_racine`, même garde-fou que
les autres routes), le parse pour affichage HTML (liste triée par date,
« Le 12 septembre 2026 à 8h — Mathématiques »), avec un bouton de
téléchargement.

Nouvelle route `GET /calendrier/<classe>/telecharger` : sert le fichier brut
avec `Content-Type: text/calendar; charset=utf-8` et un en-tête
`Content-Disposition: attachment; filename="agenda-<classe>.ics"` (nom de
fichier propre pour l'import Google Calendar, indépendant du nom interne
`.agenda.ics`).

Si le fichier n'existe pas (agenda désactivé pour cette classe, ou
`--sans-agenda` utilisé lors du scraping) : page claire « Aucun agenda
disponible pour cette classe » plutôt qu'une erreur 404 brute (cohérent avec
`page_erreur`/`MESSAGES_ERREUR` existants).

Lien vers `/calendrier/<classe>` ajouté dans la page d'accueil du viewer, à
côté du sélecteur de classe.

## 5. Limites connues (à documenter dans le README, honnêteté RGPD/UX)

- **Réimport Google Calendar = doublons.** L'import manuel d'un `.ics`
  (*Paramètres → Importer*) dans Google Calendar ne fait pas de
  déduplication par `UID` : réimporter après une nouvelle synchronisation
  recrée les événements déjà présents. Recommandation documentée dans le
  README : importer dans un calendrier secondaire dédié, et le vider avant
  de réimporter une version mise à jour.
- **Pas d'abonnement live.** Le viewer tourne en local (`127.0.0.1`), non
  joignable par Google depuis Internet : pas d'auto-rafraîchissement côté
  Google Calendar, l'utilisateur doit retélécharger et réimporter à la main
  après chaque nouvelle synchronisation.
- **Durée par défaut de 4h si une seule heure est indiquée** (voir §2) — à
  affiner si les DS de l'utilisateur ont réellement une durée différente
  visible autrement.
- **Filtre DS approximatif si le prof a fortement renommé le type**
  (ex. « Épreuve » au lieu de « Devoir surveillé ») : le filtre ne le
  détectera pas. Pas de configuration prévue dans cette version (hors-scope,
  cf. périmètre) ; solution de contour si besoin plus tard : flag
  `--agenda-types` pour élargir le filtre.

## 6. Tests

- `mois_annee_scolaire` : bascule correcte au 1er juillet (ex. `2026-09-15`
  → sept 2026 … juin 2027 ; `2027-03-01` → sept 2026 … juin 2027 ; `2026-06-30`
  → sept 2025 … juin 2026).
- `analyser_page_agenda` : page avec un DS lecture seule (bloc `<h3>`/`<h4>`/
  `<p>`) → un événement bien typé ; page avec `data-donnees` (mode édition)
  → date structurée utilisée en priorité ; page sans agenda (aucun bloc
  `<article>`) → liste vide, pas d'exception ; événement sur plusieurs jours
  (`Du … au …`) → `debut`/`fin` corrects ; matière absente → `SUMMARY` sans
  « en … ».
- `recuperer_agenda` : fusion de deux mois avec un événement en doublon
  (même `data-id`) → une seule entrée ; mock de `session.get`, aucun réseau
  réel.
- `filtrer_ds` : « Devoir surveillé » retenu, variantes de casse/accents
  retenues, « Devoir maison »/« Cours »/« Vacances » écartés.
- `generer_ics` : structure `VCALENDAR`/`VEVENT` valide, `UID` stable et
  déterministe, pliage de ligne pour un texte long, échappement d'une
  virgule/point-virgule/retour à la ligne dans la description, événement
  journée entière (`DTEND` = jour + 1), événement horodaté avec une seule

## Compatibilité

- Comportement par défaut **changé** (nouveauté assumée, comme les
  programmes de colles) : le scraper interroge désormais aussi
  `agenda?mois=…` pour chaque classe, 10 requêtes supplémentaires par
  classe et par run. Désactivable avec `--sans-agenda`.
- `.gitignore` : aucun changement nécessaire, `.agenda.ics` est déjà sous
  `cours_cdp/` (déjà ignoré intégralement).
- Le viewer reste sans dépendance tierce.
- Aucune donnée n'est envoyée à un tiers ; mention RGPD du README mise à
  jour pour citer ce nouveau flux (lecture seule de l'agenda de la classe,
  fichier `.ics` généré localement).

## Critères de réussite

- Sur une classe avec des DS programmés dans l'agenda, un run normal du
  scraper produit `.agenda.ics` avec un `VEVENT` par DS trouvé, dates
  correctes.
- `--sans-agenda` supprime tout appel vers `agenda?mois=…`.
- Le fichier généré s'importe sans erreur dans Google Calendar (vérification
  manuelle sur un vrai compte avant de considérer le chantier terminé).
- `/calendrier/<classe>` et `/calendrier/<classe>/telecharger` fonctionnent
  dans le viewer, et `.agenda.ics` n'apparaît jamais dans l'arborescence de
  documents.
- Une classe sans agenda actif (ou `--sans-agenda` utilisé) ne casse rien :
  pages/flux normaux, message clair au lieu d'une erreur.
- Suite de tests hors-ligne verte, aucun appel réseau réel dans les tests.
